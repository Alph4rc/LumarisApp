# 光序版本更新日志

为一次发版整理更新日志。同一段文字会出现在两个地方：

1. `CHANGELOG.md` —— 仓库里的版本记录
2. 附注 tag 的说明 —— CI 从 tag 的 `%(contents)` 读取它作为 `RELEASE_DESCRIPTION` 上传到发布平台（`.github/workflows/release.yml` 的 prepare job），App 内更新弹窗显示的就是这段文字

第二条决定了格式：App 里是 `Text(model.body)` 直接渲染（`lib/main_app.dart:157`），不解析 Markdown。写了 `## 新增`，用户看到的就是 `## 新增` 这几个符号。所以正文必须是纯文本。

**读者是使用光序的学生，不是开发者。** 他们只关心「更新之后多出什么、少踩什么坑」。

## 第一步：确定版本号和提交范围

`pubspec.yaml` 的 `version:` 里，`+` 之前的部分是版本号。本次要发的版本优先用用户消息里给出的；用户没给，再用下面的判断。

用脚本收集提交，不要手搓 git 命令：

```bash
bash .claude/skills/release-notes/scripts/collect_commits.sh
```

默认范围是「最近的 tag .. HEAD」。脚本会打印 pubspec 版本、tag 列表、提交清单，以及**标题看不出类型**的提交（`123`、`update` 这类）各自改了哪些文件——这类提交只能靠文件路径判断该不该收进日志。需要指定区间时传参：`collect_commits.sh <起始 ref> <结束 ref>`。

两种情况下先跟用户确认，不要自己猜：

- **pubspec 的版本号已经打过 tag**（例如 pubspec 是 `1.2.1`，tag 列表里已经有 `1.2.1`）：说明版本号还没 bump。按语义化版本建议下一个补丁号（`1.2.2`），但要用户确认这次发的是不是这个号。
- **区间为空**：HEAD 已经打过 tag 了，说明没有新提交可写，直接告诉用户，别凭空编内容。

CI 会校验 tag 与 `pubspec.yaml` 一致，不一致直接失败。所以最后交付时要提醒用户：**先改 `pubspec.yaml` 的 version 并提交，再打 tag。**

## 第二步：筛掉用户看不见的东西

| 提交 | 处理 |
| --- | --- |
| `feat` | → **新增** |
| `fix` | → **修复** |
| `perf`；用户能看出来的 `style`（排版、颜色、字号、间距） | → **优化** |
| `refactor` | 一般丢弃；只有用户能感知到行为变化时才归 **优化** |
| `chore` `ci` `test` `docs` `build`、依赖升级、纯文案措辞、发布流程改动 | 丢弃 |

没有 Conventional Commits 前缀的提交，看脚本给出的改动文件：

- 落在 `lib/ui/`、`lib/features/`、`lib/state/`，且改的是行为或界面 → 收进日志
- 只动 `.github/`、`scripts/`、`test/`、`pubspec.yaml`、`android/`、`ios/` 的配置 → 丢弃

同一个功能的多个提交要合并成一条；一次提交里混了好几个改动时也可以拆成多条。例如「添加合并同名课程功能」和「优化课程展示逻辑，合并同名课程并更新授课教师信息」说的是同一件事，只写一条。

如果整个区间没有任何用户可感知的变化（全是 CI、重构、依赖升级），直说这次没有面向用户的变化，不要硬凑——写「修复若干问题」不如不写。

## 第三步：写成用户看得懂的话

从结果出发，不写实现。判断标准：用户读完这条，能不能决定自己要不要更新。

| 提交原文 | 写进日志 |
| --- | --- |
| `fix: 修正 ScheduleTime API 路径，避免重复的版本前缀导致 404` | 修复课表时间设置偶尔加载失败的问题 |
| `feat: 调整 TodayCoursesWidget 组件的字体大小和间距` | 桌面小组件课程卡片排版更清晰 |
| `feat: 更新发布流程，改用 API Key 认证` | （丢弃，用户看不见） |

具体要求：

- 去掉类型前缀、组件名、类名、接口名、依赖名
- 每条不超过 30 字，陈述句，结尾不加句号
- 不要「若干」「一些」「部分」「其他」这类含糊词——写了等于没写。只有确实无法归纳时才用它兜底
- 整篇 3～8 条，和 1.2.0、1.1.20 这些历史版本一个量级

## 第四步：正文格式（严格照抄）

```
1.2.2

新增
· 课程卡片支持合并同名课程，教师信息去重
· 桌面小组件可以显示下周课程

修复
· 修复课表时间设置无法加载的问题

优化
· 首页磁贴加载更快，减少闪烁
```

- 第一行版本号，空行，然后各节
- 节标题只有 `新增`、`修复`、`优化` 三个，顺序固定，没有内容的节整节省略
- 每节 1～4 条，条目以 `· ` 开头
- **不要出现任何 Markdown 符号**：`#`、`*`、`-`、`**`、反引号、链接语法，它们会原样出现在用户的更新弹窗里

## 第五步：写入 CHANGELOG.md

文件不存在就创建；最新版本放最上面，老版本依次往下。版本标题带日期：

```markdown
# 更新日志

## 1.2.2 (2026-10-16)

新增
· 课程卡片支持合并同名课程，教师信息去重

修复
· 修复课表时间设置无法加载的问题
```

`CHANGELOG.md` 本身是仓库文档，用 Markdown 标题没问题；只有正文那段要保持纯文本，因为它同时是 tag 说明。动手前先读一遍已有的 `CHANGELOG.md`，跟着既有排版走，不要重排或改写历史版本的内容。

## 第六步：给出 tag 命令，不要执行

`git tag` 和 `git push` 由用户自己跑。把命令贴出来，日志正文嵌进 `-m`，单引号包住、换行原样保留：

```bash
git tag -a 1.2.2 -m '1.2.2

新增
· 课程卡片支持合并同名课程，教师信息去重

修复
· 修复课表时间设置无法加载的问题'

git push origin 1.2.2
```

正文里如果出现单引号，改用 `git tag -a <版本> -F <文件>` 指向一个临时文件。

交付时一并说明：

- 先改 `pubspec.yaml` 的 `version` 并提交，再打 tag——CI 会校验两者一致，不一致直接失败
- 推送 tag 会触发 `.github/workflows/release.yml` 自动打包发布

## 交付前自检

- 正文里有没有 Markdown 符号漏进去
- 有没有开发者术语（组件名、接口名、依赖名）
- 有没有「若干」「一些」这类含糊表述
- 每条读完能不能判断要不要更新
- 有没有漏掉用户能感知的变化，或者混进内部改动
- tag 版本号和 `pubspec.yaml` 对不对得上
